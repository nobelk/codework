# Independent review

Use a separate read-only subagent when the host and session permit delegation. Otherwise hand the packet to a different model in a separate read-only session. Include absolute artifact paths, the exact file hashes or Git revision under review, repository rules, source inputs, confirmed decisions, the focus below, and the check results. Ask for numbered findings citing a file and section or line, the consequence, and a suggested change. Keep edits and decisions in the calling session.

If neither review route is available, give the user the packet and mark independent review pending. If a report makes claims without showing which artifact it read, request a review with citations. Record the reviewer, revision, and findings or pending status. Recheck revised artifacts before reporting their status.

## Review focus

Review the product requirements document at <absolute document path>. The review context may list this file as skipped because of its size; open it at that path and read it in full before reviewing. Also read README.md, AGENTS.md, GEMINI.md, and repository guidance, anything under specs/, and the source code wherever the document describes existing behaviour. Review only this document; ignore other working-tree changes. Its requirements are written in EARS (Easy Approach to Requirements Syntax): "WHERE <feature>, WHILE <state>, WHEN <trigger>, IF <unwanted condition>, THEN the <system name> SHALL <response>", every clause before the system name optional, one response per requirement. Look for: requirements that break that syntax; a keyword that misstates the behaviour (WHEN for a lasting state, WHILE for an instant event, WHEN for an error or failure that should be IF ... THEN); missing unwanted behaviour for an event-driven requirement (invalid input, a missing permission, a duplicate request, a dependency failing, a limit reached, a conflicting change, an interruption, missing data); requirements that are not testable (no number or unit, vague words, an unverifiable negative); requirements that say how rather than what (components, storage, frameworks, algorithms, screen layouts) and are not listed as constraints; requirements that contradict or duplicate each other, or deliver something listed under "What we're not doing"; goals without a measurable metric, baseline, and target, and goals that no requirement serves; user stories that no requirement implements, and requirements that trace to nothing; priorities that conflict with the stated MVP or target release; non-functional targets missing the conditions they are measured under (load, percentile, period); statements about existing behaviour that contradict the code; assumptions the requirements depend on but do not state; open questions that block a Must requirement; and terms used but not in the glossary, or used with two meanings. For each finding, output a numbered item with the section and requirement ID, the issue, and the suggested change. Output findings only; do not rewrite the document.
